# IntelliBird v2.0 — Fresh-deploy Smoke Runbook

Operator gate between "Phase 13 code complete" and "v2.0 tagged". Walks a
clean Docker host through a full stack bring-up, validates the seven PROD-01
through PROD-07 success criteria from the deployed state, and hands off the
`v2.0` tag command to the operator. Claude does not execute any `git` command
in this runbook — per `memory/feedback_no_auto_commit.md`, all commits and
tags in this repo are authored by `Lavender-dll <github@securescape.cc>`.

Related: [`auth-setup.md`](auth-setup.md) (initial Authentik provisioning),
[`secret-rotation.md`](secret-rotation.md) (PROD-04 drill),
[`authentik-recovery.md`](authentik-recovery.md) (PROD-06 drill),
[`load-test-results.md`](load-test-results.md) (PROD-05 evidence).

## Overview

- **When:** Once, immediately before cutting the `v2.0` git tag.
- **Where:** A clean Docker host (fresh VM, or `docker compose down -v` on
  an otherwise-idle dev host). Do NOT run this against a populated staging
  stack — the fresh-deploy property is what gets tested.
- **Who:** Operator. Claude is not expected to execute any step below.
- **Outcome:** All 8 smoke checks PASS + the `## Last Smoke` section filled
  + `v2.0` tag cut by the operator on the smoke-tested commit.

## Fresh Deploy Procedure

Run from a shell on the clean Docker host.

```bash
# 1. Clone + checkout the release-candidate branch.
git clone https://github.com/Whispergate/IntelliBird.git
cd IntelliBird
git checkout <release-candidate-branch>   # e.g. dev-0.0.1 at the RC commit

# 2. Seed ops/.env from the example and fill the required secrets.
cp ops/.env.example ops/.env
# Edit ops/.env:
#   AUTH_ENABLED=true
#   JWT_SIGNING_KEY=$(openssl rand -hex 32)
#   SETUP_TOKEN=$(openssl rand -hex 16)       # one-time first-admin bootstrap
#   SSO_ISSUER_URL=http://authentik:9000/application/o/intellibird/
#   SSO_CLIENT_ID=<from Authentik Providers → intellibird>
#   SSO_CLIENT_SECRET=<from Authentik Providers → intellibird>
#   POSTGRES_PASSWORD=$(openssl rand -hex 24)
#   SECRET_KEY=$(openssl rand -hex 32)
# (Authentik provisioning: docs/ops/auth-setup.md §7 — run the `sso` profile
# first, create the OIDC provider, then copy client id/secret here.)

# 3. Ensure the api entrypoint is executable (known gap from 13-04).
chmod +x ops/api-entrypoint.sh

# 4. Bring up the stack.
docker compose -f ops/docker-compose.yml --profile sso up -d   # if using Authentik
# or, if Authentik runs elsewhere:
# docker compose -f ops/docker-compose.yml up -d

# 5. Wait for api health.
timeout 120 bash -c 'until curl -sfk https://localhost/healthz; do sleep 3; done'
```

If step 5 times out, `docker compose logs api caddy` — most likely culprits:
AUTH_ENABLED unset (entrypoint exits 78), JWT_SIGNING_KEY unset (entrypoint
exits on `${VAR:?}`), or Caddy cannot reach `api:8000` because api failed
the healthcheck.

## Smoke Checks

Each check has an expected output. Record PASS/FAIL + output excerpt into
the `## Last Smoke` block below per check. Do not continue past a FAIL —
diagnose, re-rehearse the upstream plan, re-run from "Fresh Deploy" on a
wiped host.

### 1. Caddy serves healthz over TLS on the public edge

```bash
curl -fsS -k https://localhost/healthz
```

**Expected:** HTTP 200; body `{"ok":true}` (or equivalent healthz payload).
Caddy's self-signed `tls internal` cert is in use on the lab stack — `-k`
bypasses the cert chain check, which is correct for `tls internal`.

### 2. api is NOT publicly reachable on 8000

```bash
curl -fsS -o /dev/null -w "http_code=%{http_code}\n" \
  --max-time 5 http://localhost:8000/healthz || echo "connection refused (expected)"
```

**Expected:** `connection refused` OR non-200 from nothing listening on
host port 8000. A 200 here means `ops/docker-compose.yml` reintroduced a
host-port publish on the api service — stop, investigate, do NOT tag v2.0.
Covers the compose binding contract from PROD-07.

### 3. Authentik SSO login round-trip (browser)

1. Open `https://localhost/login` in an incognito browser window (accept
   the self-signed cert warning once).
2. Click **Sign in with Authentik** → redirected to Authentik.
3. Authenticate as a test user in `intellibird-analysts`.
4. Redirected back to `/red` or `/blue`. Role badge matches group → role
   mapping (`auth-setup.md` §8).
5. Copy the access token from browser devtools (Application → Cookies →
   `intellibird_session` / bearer depending on stack). Stash as
   `BLUE_JWT` for check 4.

**Expected:** Full round-trip succeeds; `/api/auth/me` returns
`{"role":"Analyst", ...}` for the test user. Failure modes match the table
in `authentik-recovery.md` §4.

### 4. X-Dashboard-Role spoof is rejected (PROD-03 defense-in-depth)

With a Blue-role JWT, send `X-Dashboard-Role: red` through Caddy:

```bash
curl -sk -o /tmp/events.json -w "http_code=%{http_code}\n" \
  https://localhost/api/events \
  -H "X-Dashboard-Role: red" \
  -H "Authorization: Bearer $BLUE_JWT"

jq '.items | map(.visibility) | unique' /tmp/events.json
```

**Expected:** `http_code=200`; visibility set is a subset of Blue-visible
values (`shared`, `blue_only`); NO `red_only` items present. Both layers
must hold:
(a) Caddy stripped the header before it reached api
(`ops/Caddyfile: request_header -X-Dashboard-Role`),
(b) even if the header had arrived, api derives role from the JWT claim
only — the regression suite covers both in
`test_prod03_dashboard_role_spoof.py`.

### 5. Entrypoint refuses to start without AUTH_ENABLED

On the host, with the stack down:

```bash
docker compose -f ops/docker-compose.yml down
AUTH_ENABLED="" JWT_SIGNING_KEY="x" \
  docker compose -f ops/docker-compose.yml up api
# Observe: api container exits 78 (EX_CONFIG); logs contain
#   "FATAL: AUTH_ENABLED is not 'true'."
docker compose -f ops/docker-compose.yml ps api   # State: Exit 78
docker compose -f ops/docker-compose.yml down
```

Restore `ops/.env` to the working values and `up -d` the full stack before
proceeding to check 6.

**Expected:** Exit code 78 with the 4-line operator message in stderr.
Covers PROD-07 entrypoint guard from deployed state (the integration tests
cover the same path via `run_entrypoint` harness).

### 6. EASM active-scan gate rejects unauthorised active scan (PROD-02)

Pick a project with `active_scans_authorised=false` (fresh deploy default)
and an Admin/Analyst JWT:

```bash
PROJECT_ID=<uuid of a project in the stack>
curl -sk -o /tmp/scan.json -w "http_code=%{http_code}\n" \
  -X POST https://localhost/api/easm/scans \
  -H "Authorization: Bearer $ANALYST_JWT" \
  -H "Content-Type: application/json" \
  -d "{\"project_id\":\"$PROJECT_ID\",\"active\":true,\"modules\":[\"httpx\"]}"

jq . /tmp/scan.json
```

**Expected:** `http_code=403`; response body indicates missing gate fields
(`active_scans_authorised`, `scope_acknowledgement_text`,
`active_auth_confirmed_at`). Reproduces the `test_prod02_active_scan_gate`
regression path end-to-end through Caddy.

### 7. Caddy TLS certificate is valid (self-signed or ACME)

```bash
echo | openssl s_client -connect localhost:443 -servername localhost 2>/dev/null \
  | openssl x509 -noout -issuer -subject -dates
```

**Expected on a lab stack (`tls internal`):** issuer contains
`Caddy Local Authority`; dates are present and not-yet-expired. **Expected
on a production hostname with ACME enabled:** issuer is Let's Encrypt R3 /
R11; `notAfter` > 30 days out. Note: a production deploy requires editing
`ops/Caddyfile` per the header comment before smoke (swap `:443, :80` for
the real hostname + remove `tls internal`).

### 8. Only Caddy publishes 80/443 (no drift from compose)

```bash
docker compose -f ops/docker-compose.yml ps --format json \
  | jq -r 'select(.Publishers != null) | "\(.Service)\t\(.Publishers | map(.PublishedPort) | unique | tostring)"'
```

**Expected output (one line per service that publishes anything on a public
interface):**

```
caddy   [80,443]
db      [5432]     # 127.0.0.1-bound — operator-local tooling
redis   [6379]     # 127.0.0.1-bound — operator-local tooling
```

`api` and `web` MUST NOT appear. `db`/`redis` publishes must be
`127.0.0.1`-bound (inspect via `docker compose -f ops/docker-compose.yml
port db 5432` — should print `127.0.0.1:5432`, not `0.0.0.0:5432`). Any
other service on a non-loopback interface → FAIL.

## Cut v2.0

**Only after the whole Preconditions Checklist is ticked AND every smoke
check is PASS.** The operator (Lavender-dll) executes these commands — not
Claude.

```bash
# 1. Confirm you are on the exact smoke-tested commit.
git rev-parse HEAD
# Paste this sha into the "Tagged commit sha" field of Last Smoke above.

# 2. Tag. Annotated, signed if your setup signs tags.
git tag -a v2.0 -m "IntelliBird v2.0 — production-ready milestone"

# 3. Inspect before pushing.
git tag -l v2.0
git show v2.0 --stat | head -40

# 4. Push the tag when you are ready for the release.
git push origin v2.0
```

### If the smoke failed

Do NOT cut `v2.0`. Open a gap-closure plan via
`/gsd:plan-phase 13 --gaps`, fix, re-rehearse the failing plan's
checkpoint, re-run the full smoke from "Fresh Deploy" on a wiped host.

### If the smoke passed but a regression surfaces post-tag

Cut `v2.0.1` (or higher). **Never amend `v2.0`** — the tag points at the
smoke-tested commit, which is the auditable production-ready artefact.
Amending destroys that audit trail.

```bash
# After fixing on a new commit:
git tag -a v2.0.1 -m "IntelliBird v2.0.1 — <short-reason>"
git push origin v2.0.1
```
